# 운영체제 10장 가상 메모리

## 1. 가상 메모리

프로그램을 실행하려면 필요한 코드와 데이터가 물리 메모리에 있어야 한다.
가장 단순한 방법은 프로세스 전체를 메모리에 올리는 것이지만, 이 방식은 프로그램의 크기를 물리 메모리 크기로 제한한다.

실제로 프로그램에는 거의 실행되지 않는 오류 처리 코드나 사용하지 않는 기능이 포함되어 있고, 배열이나 테이블도 실제 사용량보다 크게 선언되는 경우가 있다.
프로그램 전체를 한꺼번에 메모리에 올리지 않고 필요한 부분만 적재할 수 있다면 물리 메모리를 더 효율적으로 사용할 수 있다.

가상 메모리는 프로세스가 바라보는 논리적인 메모리와 실제 물리 메모리를 분리하는 기술이다.
프로그램은 물리 메모리보다 큰 가상 주소 공간을 사용하는 것처럼 실행할 수 있고, 운영체제는 필요한 페이지만 물리 메모리에 올린다.

가상 메모리를 사용하면 다음과 같은 이점이 있다.

- 프로그램이 물리 메모리 크기에 직접 제한받지 않는다.
- 각 프로그램이 실제로 사용하는 메모리가 줄어들어 더 많은 프로그램을 동시에 실행할 수 있다.
- 응답 시간을 유지하면서 CPU 이용률과 처리량을 높일 수 있다.
- 프로세스 전체를 메모리와 보조 저장장치 사이에서 옮기는 I/O가 줄어든다.

### 가상 주소 공간

프로세스가 보는 가상 주소 공간은 일반적으로 연속된 공간처럼 구성된다.
반면 물리 메모리는 여러 페이지 프레임으로 나뉘어 있고, 한 프로세스에 할당된 프레임들이 물리적으로 연속되어 있을 필요는 없다.
MMU와 페이지 테이블이 가상 페이지를 물리 프레임에 매핑한다.

가상 주소 공간에서 힙은 동적 할당에 따라 위쪽으로 확장되고, 스택은 함수 호출에 따라 아래쪽으로 확장된다.
힙과 스택 사이의 빈 공간은 실제로 접근될 때까지 물리 페이지를 할당받지 않는다.
이처럼 실제로 사용되지 않는 공간을 포함한 주소 공간을 희소 주소 공간(sparse address space)이라고 한다.

가상 메모리는 페이지 공유도 가능하게 한다.
여러 프로세스가 같은 파일이나 메모리를 사용해야 할 때 각 프로세스의 가상 주소 공간에는 같은 물리 페이지를 매핑할 수 있다.

## 2. 요구 페이징

가상 메모리에서 페이지를 실제로 참조할 때 메모리에 적재하는 방식을 **요구 페이징(Demand Paging)**이라고 한다.
사용되지 않는 페이지는 물리 메모리에 올리지 않고 보조 저장장치에 둔다.

페이지가 메모리에 있는지는 페이지 테이블의 valid-invalid bit로 확인한다.

- `valid`: 페이지가 유효하고 물리 메모리에 존재한다.
- `invalid`: 가상 주소 공간에 정의되지 않은 잘못된 페이지이거나, 유효하지만 현재 물리 메모리에 없는 페이지다.

페이지 테이블 항목이 `invalid`라고 해서 바로 문제가 발생하는 것은 아니다.
프로세스가 해당 페이지에 접근할 때 운영체제가 페이지 폴트를 처리한다.

### 페이지 폴트 처리 과정

페이지 테이블에서 invalid bit를 확인하면 하드웨어는 운영체제에 page fault trap을 발생시킨다.
운영체제는 다음 순서로 페이지를 처리한다.

1. 프로세스의 내부 테이블을 확인해 메모리 참조가 유효한지 검사한다.
2. 가상 주소 자체가 잘못된 참조라면 프로세스를 종료한다.
3. 유효한 주소지만 페이지가 메모리에 없는 경우 가용 프레임을 찾는다.
4. 가용 프레임이 없다면 페이지 교체로 희생 프레임을 확보한다.
5. 보조 저장장치에서 필요한 페이지를 확보한 프레임으로 읽어 온다.
6. 페이지 테이블에 프레임 번호를 기록하고 valid 상태로 갱신한다.
7. 페이지 폴트를 발생시킨 명령어를 다시 실행한다.

페이지를 보조 저장장치에서 읽어 오는 동안에는 디스크 I/O가 발생한다.
트랩 처리, 주소 유효성 검사, 페이지 테이블 갱신보다도 저장장치 I/O가 훨씬 느리기 때문에 페이지 폴트가 자주 발생하면 전체 성능이 크게 떨어진다.
I/O가 진행되는 동안 운영체제는 다른 프로세스에 CPU를 할당할 수도 있다.

운영체제는 페이지 폴트 처리를 빠르게 하기 위해 **가용 프레임 리스트(Free Frame List)**를 유지한다.
프로세스의 스택이나 힙이 확장될 때도 이 리스트에서 프레임을 할당한다.
새 프레임을 할당하기 전 0으로 채우는 **Zero-fill-on-demand**를 사용하면 이전 프로세스의 데이터가 새 프로세스에 노출되는 것을 막을 수 있다.

### 순수 요구 페이징

**순수 요구 페이징(Pure Demand Paging)**은 프로세스를 시작할 때 페이지를 하나도 미리 적재하지 않고, 실제 참조가 발생할 때만 페이지를 가져오는 방식이다.

처음에는 메모리에 페이지가 없어도 프로세스를 시작할 수 있다.
첫 번째 명령어가 있는 페이지에 접근하는 순간 페이지 폴트가 발생하고, 해당 페이지가 적재된 뒤 명령어를 다시 실행한다.
이후에도 프로세스가 새로운 페이지를 참조할 때마다 같은 과정이 반복된다.

프로그램은 보통 한 시점에 일부 페이지를 집중적으로 참조하는 지역성(Locality)을 가진다.
이 때문에 모든 페이지를 한꺼번에 적재하지 않아도 페이지 폴트가 지나치게 자주 발생하는 상황을 어느 정도 피할 수 있다.

## 3. Copy-on-Write

**Copy-on-Write(COW)**는 부모 프로세스와 자식 프로세스가 처음에는 같은 물리 페이지를 공유하고, 쓰기가 발생할 때만 페이지를 복사하는 방식이다.

`fork()`를 호출할 때 부모 프로세스의 메모리를 전부 즉시 복사하면 시간과 메모리가 많이 필요하다.
하지만 `fork()` 직후 `exec()`가 실행된다면 부모의 메모리 대부분은 자식 프로세스에서 사용되지 않는다.

그래서 운영체제는 부모와 자식의 페이지 테이블이 같은 물리 페이지를 가리키게 하고, 공유 페이지를 읽기 전용으로 표시한다.

1. 부모와 자식이 같은 물리 페이지를 공유한다.
2. 둘 중 하나가 공유 페이지에 쓰기를 시도한다.
3. 읽기 전용 페이지에 대한 쓰기 때문에 페이지 폴트가 발생한다.
4. 운영체제가 새 프레임을 할당하고 기존 페이지를 복사한다.
5. 쓰기를 시도한 프로세스의 페이지 테이블을 새 프레임으로 변경한다.
6. 쓰기 권한을 부여하고 중단된 명령어를 다시 실행한다.

읽기만 하는 동안에는 복사하지 않으므로 `fork()`의 비용과 메모리 사용량을 줄일 수 있다.

## 4. 페이지 교체

프로세스가 계속 실행되면 모든 물리 프레임이 사용 중인 상태가 될 수 있다.
이때 메모리에 없는 새 페이지를 적재하려면 현재 메모리에 있는 페이지 중 하나를 내보내 프레임을 확보해야 한다.
이 과정을 **페이지 교체(Page Replacement)**라고 한다.

가용 프레임이 없는 상태에서 페이지 폴트가 발생하면 운영체제는 다음 과정을 수행한다.

1. 메모리에 있는 페이지 중 희생 페이지(victim)를 선택한다.
2. 희생 페이지가 수정된 상태라면 보조 저장장치에 기록한다.
3. 희생 페이지가 사용하던 프레임을 해제한다.
4. 필요한 페이지를 해당 프레임에 적재한다.
5. 페이지 테이블과 관련 자료구조를 갱신한다.
6. 페이지 폴트를 발생시킨 명령어를 다시 실행한다.

페이지 교체 알고리즘의 목표는 페이지 폴트 횟수를 줄이는 것이다.
알고리즘을 비교할 때는 메모리 접근 순서를 나타내는 **참조 문자열(Reference String)**을 사용한다.
프레임 수가 많으면 일반적으로 페이지 폴트가 줄어들지만, 실제 시스템에서는 프레임 수가 제한되어 있으므로 교체 정책이 중요하다.

### FIFO

**FIFO(First-In, First-Out)**는 메모리에 가장 먼저 들어온 페이지를 가장 먼저 내보내는 방식이다.
큐로 구현하기 쉬워 간단하지만, 페이지가 실제로 얼마나 자주 사용되는지는 고려하지 않는다.

FIFO에서는 프레임 수를 늘렸는데도 페이지 폴트가 증가하는 **Belady's Anomaly**가 발생할 수 있다.
프레임을 많이 할당하면 항상 성능이 좋아진다는 보장이 없는 셈이다.

### Optimal Page Replacement

**최적 페이지 교체(OPT)**는 앞으로 가장 오랫동안 사용되지 않을 페이지를 교체한다.
이론적으로 페이지 폴트가 가장 적게 발생하지만, 미래의 메모리 접근을 미리 알아야 하므로 실제 운영체제에서 구현할 수 없다.

OPT는 실제 알고리즘이라기보다 다른 페이지 교체 알고리즘의 성능을 비교하는 기준으로 사용된다.

### LRU

**LRU(Least Recently Used)**는 가장 오랫동안 사용되지 않은 페이지를 교체한다.
최근에 사용된 페이지는 가까운 미래에도 다시 사용될 가능성이 높다는 지역성을 이용한다.

LRU는 OPT처럼 미래를 알 수는 없지만, 최근 사용 기록으로 미래의 사용 가능성을 추정한다.
성능이 좋은 편이지만 모든 페이지의 최근 사용 순서를 관리해야 하므로 구현 비용이 크다.

대표적인 구현 방법은 다음과 같다.

- **계수기 방식**: 페이지마다 마지막 사용 시각을 기록하고 가장 오래된 페이지를 찾는다.
- **스택 방식**: 최근 사용한 페이지를 스택의 위쪽으로 옮긴다. 가장 아래에 있는 페이지가 가장 오래 사용되지 않은 페이지다.

### LRU 근사

정확한 LRU는 비용이 크기 때문에 운영체제는 하드웨어가 제공하는 **Reference Bit**를 이용해 LRU를 근사할 수 있다.
페이지가 참조되면 reference bit를 `1`로 표시하고, 교체 여부를 판단할 때 이 값을 활용한다.

#### Additional-Reference-Bits Algorithm

페이지마다 여러 개의 reference bit를 두고 일정한 주기마다 비트를 오른쪽으로 이동시킨다.
최근에 자주 참조된 페이지는 큰 값을 가지고, 값이 작은 페이지를 교체 대상으로 선택한다.

#### Second-Chance Algorithm

Second-Chance는 FIFO에 reference bit를 추가한 방식이다.

- reference bit가 `0`이면 해당 페이지를 교체한다.
- reference bit가 `1`이면 최근에 사용된 페이지로 보고 bit를 `0`으로 바꾼 뒤 교체를 미룬다.
- 다음 페이지를 같은 방식으로 확인한다.

FIFO의 단순함을 유지하면서 최근에 사용된 페이지가 바로 제거되는 문제를 줄일 수 있다.

#### Enhanced Second-Chance Algorithm

reference bit뿐 아니라 수정 여부를 나타내는 **Modify Bit(Dirty Bit)**도 함께 사용한다.
페이지의 상태를 `(R, M)`으로 표현하고 다음 순서로 교체를 선호한다.

```text
(0, 0) → (0, 1) → (1, 0) → (1, 1)
```

최근에 참조되지 않았고 수정되지 않은 `(0, 0)` 페이지는 저장장치에 다시 기록할 필요도 없으므로 가장 좋은 희생 페이지다.

### Counting-Based Page Replacement

각 페이지가 참조된 횟수를 counter로 기록하고, 그 값을 기준으로 희생 페이지를 선택하는 방식이다.

- **LFU(Least Frequently Used)**: 참조 횟수가 가장 적은 페이지를 교체한다.
- **MFU(Most Frequently Used)**: 참조 횟수가 가장 많은 페이지를 교체한다. 참조 횟수가 적은 페이지가 최근에 들어와 아직 충분히 사용되지 않았다고 보는 방식이다.

LFU와 MFU는 counter를 관리해야 하고, 일반적인 LRU 근사보다 성능이 좋지 않은 경우가 많아 널리 사용되지는 않는다.

### Page-Buffering Algorithm

페이지 교체가 필요할 때마다 프레임을 찾는 대신, 운영체제가 일정 수의 가용 프레임을 미리 확보해 두는 방식이다.
페이지 폴트가 발생하면 확보해 둔 프레임에 바로 페이지를 적재할 수 있다.

교체한 페이지를 잠시 보존해 두면 다시 필요할 때 디스크에서 읽지 않고 복구할 수 있다.
수정된 페이지를 별도로 기록해 두는 방식도 페이지 폴트 처리 시간을 줄이는 데 도움이 된다.

## 5. 프레임 할당

여러 프로세스가 동시에 실행되면 운영체제는 사용 가능한 물리 프레임을 각 프로세스에 나누어 주어야 한다.
한 프로세스에 너무 적은 프레임을 할당하면 페이지 폴트가 자주 발생하고, 특정 프로세스에 너무 많이 할당하면 다른 프로세스가 사용할 프레임이 부족해진다.

### 최소 프레임 수

프로세스가 명령어를 정상적으로 실행하려면 최소한의 프레임이 필요하다.
하나의 명령어가 명령어 자체와 여러 메모리 피연산자를 동시에 참조한다면, 해당 페이지들을 한 번에 메모리에 유지할 수 있어야 명령어 실행을 끝낼 수 있다.
이 최소 프레임 수는 CPU의 명령어 집합 구조(ISA)에 따라 달라진다.

최대로 할당할 수 있는 프레임 수는 시스템의 전체 물리 프레임 수에 의해 제한된다.

### 할당 알고리즘

사용 가능한 프레임을 `m`개, 프로세스를 `n`개라고 하자.

- **균등 할당(Equal Allocation)**: 모든 프로세스에 같은 수의 프레임을 할당한다.
- **비례 할당(Proportional Allocation)**: 프로세스 크기가 클수록 더 많은 프레임을 할당한다.

  ```text
  aᵢ = (sᵢ / Σsⱼ) × m
  ```

  `sᵢ`는 프로세스의 크기, `aᵢ`는 프로세스에 할당할 프레임 수다.
- **우선순위 할당(Priority Allocation)**: 중요한 프로세스에 더 많은 프레임을 할당한다.

균등 할당과 비례 할당은 프로세스의 중요도를 고려하지 않는다.
응답이 중요한 프로세스가 있다면 크기뿐 아니라 우선순위를 함께 반영할 수 있다.

### 전역 교체와 지역 교체

페이지 교체에서 희생 페이지를 어느 범위에서 찾을지도 정해야 한다.

- **전역 교체(Global Replacement)**: 다른 프로세스에 할당된 프레임까지 희생 페이지 후보에 포함한다.
  - 전체 메모리를 유연하게 사용할 수 있다.
  - 한 프로세스의 페이지 폴트가 다른 프로세스의 성능에 영향을 줄 수 있다.
- **지역 교체(Local Replacement)**: 해당 프로세스에 할당된 프레임 안에서만 희생 페이지를 선택한다.
  - 프로세스 간 영향이 적고 실행 시간을 예측하기 쉽다.
  - 사용하지 않는 프레임이 있어도 다른 프로세스가 활용하기 어렵다.

전역 교체는 시스템 전체의 효율을 높이기 쉽고, 지역 교체는 프로세스 간 격리와 예측 가능성을 유지하기 쉽다.

### NUMA

멀티프로세서 시스템에서는 CPU와 메모리 사이의 접근 시간이 항상 같지 않을 수 있다.
여러 CPU 소켓을 사용하는 서버는 CPU마다 가까운 메모리 노드를 가지는데, 이런 구조를 **NUMA(Non-Uniform Memory Access)**라고 한다.

CPU가 가까운 노드의 메모리에 접근하는 것은 **Local Memory Access**이고, 다른 노드의 메모리에 접근하는 것은 **Remote Memory Access**다.
Remote 접근이 반복되면 메모리 지연 시간이 커진다.

따라서 NUMA 시스템에서는 단순히 빈 프레임을 찾는 것보다 프로세스가 실행되는 CPU와 가까운 노드의 프레임을 할당하는 것이 중요하다.
CPU 스케줄링과 메모리 할당을 완전히 독립된 문제로 보기 어려운 이유다.

#### First Touch

페이지를 처음 접근한 스레드가 속한 NUMA 노드에 페이지를 할당하는 방식을 **First Touch**라고 한다.

```text
Thread 0 (Node 0) → 큰 메모리 영역 초기화 → 대부분의 페이지가 Node 0에 할당

프로세스를 Node 1에 고정

Thread 1 (Node 1) → 같은 메모리 영역을 계속 사용 → Remote Memory Access 증가
```

처음 초기화할 때와 실제 사용할 CPU의 위치가 다르면 페이지가 먼 노드에 배치될 수 있다.

## 6. 스래싱

프로세스에 필요한 프레임이 충분하지 않아 페이지 폴트와 페이지 교체가 지나치게 자주 발생하는 현상을 **스래싱(Thrashing)**이라고 한다.
CPU가 실제 프로세스 작업보다 페이지를 교체하는 데 더 많은 시간을 쓰게 되므로 처리량과 CPU 이용률이 함께 떨어진다.

스래싱은 다음과 같은 흐름으로 악화된다.

```text
메모리 부족
  → 페이지 폴트 증가
  → 프로세스가 I/O를 기다림
  → CPU 이용률 감소
  → 운영체제가 프로세스를 더 추가
  → 프로세스당 프레임 감소
  → 페이지 폴트가 더 증가
```

페이지 교체가 필요한데 현재 활발하게 사용되는 페이지 중 하나를 내보내면, 곧바로 그 페이지가 다시 필요해진다.
이 페이지를 다시 읽어 오는 동안 또 다른 페이지가 제거되고, 같은 과정이 반복된다.

### 작업 집합 모델

프로그램은 모든 페이지를 고르게 참조하지 않고 특정 페이지 집합을 집중적으로 참조하는 지역성을 가진다.
최근 `Δ`개의 페이지 참조를 하나의 창(window)으로 보고, 그 안에서 실제로 참조된 서로 다른 페이지들의 집합을 **작업 집합(Working Set)**이라고 한다.

프로세스 `i`의 작업 집합 크기를 `WSSᵢ`라고 하면, 현재 프로세스가 원활하게 실행되기 위해 필요한 프레임 수를 근사할 수 있다.
모든 프로세스의 작업 집합 크기 합을 `D`라고 할 때,

```text
D = ΣWSSᵢ
```

`D`가 사용 가능한 전체 프레임 수보다 크면 모든 프로세스에 필요한 메모리를 동시에 제공할 수 없다.
이때 일부 프로세스를 중단하거나 swap out하여 다중 프로그래밍 정도를 낮추면 스래싱을 완화할 수 있다.

### 페이지 폴트 빈도

작업 집합을 직접 추적하는 대신 **Page-Fault Frequency(PFF)**를 감시할 수도 있다.
페이지 폴트율에 상한과 하한을 정해 두고 프로세스의 프레임 수를 조정한다.

- 페이지 폴트율이 상한보다 높으면 프레임이 부족하다고 판단해 프레임을 더 할당한다.
- 페이지 폴트율이 하한보다 낮으면 필요 이상으로 프레임을 사용한다고 판단해 일부 프레임을 회수한다.
- 추가로 제공할 프레임이 없다면 일부 프로세스를 중단해 프레임을 확보한다.

## 7. 메모리 압축

메모리가 부족할 때 일부 페이지를 압축해 RAM에 보관하는 방법도 있다.
디스크 I/O는 매우 느리므로, 압축과 해제에 CPU 연산 비용이 들더라도 디스크로 swap하는 것보다 빠를 수 있다.

압축된 페이지가 다시 필요해지면 압축을 해제해 원래 페이지로 복원한 뒤 사용한다.
메모리 압축은 CPU 비용과 디스크 I/O 비용 사이의 균형을 고려한 방법이다.

## 8. 커널 메모리 할당

커널 메모리는 일반 프로세스의 메모리와 다른 방식으로 할당한다.
커널은 단편화로 인한 낭비를 줄여야 하고, 장치 I/O처럼 물리적으로 연속된 메모리가 필요한 작업도 처리해야 하기 때문이다.

### 버디 시스템

**버디 시스템(Buddy System)**은 물리적으로 연속된 페이지들로 구성된 블록을 할당한다.
요청한 크기를 담을 수 있는 가장 작은 `2ⁿ` 크기의 블록을 선택한다.

처음에는 전체 메모리를 하나의 큰 블록으로 보고, 요청한 크기에 맞을 때까지 블록을 절반씩 나눈다.
블록을 해제하면 서로 인접한 버디 블록인지 확인하고, 가능하면 다시 하나의 큰 블록으로 합친다.

2의 거듭제곱 크기로만 블록을 나누기 때문에 내부 단편화가 생길 수 있다.
대신 인접한 블록을 빠르게 합칠 수 있다는 장점이 있다.

### 슬랩 할당

**슬랩 할당(Slab Allocation)**은 커널 객체를 위한 객체 캐시를 미리 만들어 두고, 같은 크기의 객체를 빠르게 할당하고 해제하는 방식이다.

커널이 부팅될 때 객체 캐시를 만들고, 캐시가 부족하면 상위 메모리 할당기에 새로운 슬랩을 요청한다.
슬랩 안의 객체가 더 이상 사용되지 않으면 상위 할당기에 반환할 수 있다.

객체를 미리 초기화해 두므로 매번 객체를 만들고 초기화하는 비용을 줄일 수 있다.
작은 커널 객체를 반복해서 할당하는 상황에서 오버헤드와 내부 단편화를 줄이는 데 도움이 된다.

## 9. 가상 메모리의 추가 고려 사항

### Prepaging

**Prepaging**은 프로세스가 곧 사용할 것으로 예상되는 페이지를 페이지 폴트가 발생하기 전에 미리 적재하는 방식이다.
프로세스 시작이나 재시작 직후 페이지 폴트가 연속해서 발생하는 문제를 줄일 수 있다.

하지만 미리 가져온 페이지를 실제로 사용하지 않으면 불필요한 I/O와 메모리 낭비가 생긴다.
페이지 폴트를 줄이는 이득과 사용되지 않을 페이지를 가져오는 비용 사이의 trade-off가 있다.

### 페이지 크기

페이지 크기는 페이지 테이블의 크기, I/O 효율, 내부 단편화에 영향을 준다.

| 페이지 크기 | 장점 | 단점 |
| --- | --- | --- |
| 작음 | 필요한 데이터만 세밀하게 적재하고 내부 단편화를 줄인다. | 페이지 수와 페이지 테이블 크기가 늘어난다. |
| 큼 | 페이지 테이블 크기가 줄고 한 번의 I/O로 많은 데이터를 가져온다. TLB Reach도 커진다. | 사용하지 않는 데이터까지 적재되어 내부 단편화와 메모리 낭비가 커질 수 있다. |

작은 페이지는 메모리를 세밀하게 사용하기 좋고, 큰 페이지는 주소 변환과 I/O 효율을 높이기 좋다.

### TLB Reach

**TLB Reach**는 TLB가 페이지 테이블을 다시 참조하지 않고 커버할 수 있는 메모리 영역의 크기다.

```text
TLB Reach = TLB 엔트리 수 × 페이지 크기
```

프로세스의 작업 집합이 TLB Reach보다 크면 TLB에 모든 주소 변환 정보를 유지할 수 없어 TLB miss가 자주 발생할 수 있다.
페이지 크기를 4KB에서 2MB Huge Page로 늘리면 하나의 TLB 엔트리가 더 넓은 영역을 담당해 TLB miss를 줄이는 데 도움이 된다.
대신 큰 페이지는 내부 단편화와 사용하지 않는 데이터의 적재를 늘릴 수 있다.

### 역 페이지 테이블

일반적인 페이지 테이블은 가상 페이지마다 페이지 테이블 항목을 가진다.
가상 주소 공간이 커지면 페이지 테이블 자체가 많은 메모리를 차지할 수 있다.

**역 페이지 테이블(Inverted Page Table)**은 물리 프레임마다 하나의 항목을 유지한다.
각 물리 프레임에 어떤 프로세스의 가상 페이지가 저장되어 있는지를 기록하므로 페이지 테이블에 필요한 메모리를 줄일 수 있다.

대신 가상 페이지가 메모리에 있는지 찾는 과정이 복잡해질 수 있고, 메모리에 없는 페이지의 보조 저장장치 위치를 찾기 위해 프로세스별로 확장된 페이지 테이블을 별도로 유지할 수 있다.
이 보조 테이블은 페이지 폴트가 발생했을 때 주로 사용되므로 일반 페이지 테이블처럼 빠른 주소 변환 경로에 놓일 필요는 없다.

### 프로그램 구조와 지역성

페이지 교체 성능은 페이지 교체 알고리즘뿐 아니라 프로그램의 메모리 접근 패턴에도 영향을 받는다.
프로그램이 지역성을 잘 활용하도록 코드와 데이터의 접근 패턴을 설계하면 필요한 작업 집합의 크기와 페이지 폴트 발생을 줄일 수 있다.

### I/O 상호 잠금과 페이지 고정

장치가 사용자 메모리의 특정 페이지를 직접 읽거나 쓰는 동안 해당 페이지가 교체되면 문제가 생긴다.
I/O가 끝나기 전에 프레임이 다른 페이지에 재사용되면, 기존 I/O의 결과가 새로운 페이지를 덮어쓸 수 있다.

```text
1. Disk → Frame 10으로 I/O 시작
2. 페이지 교체 발생
3. Frame 10을 다른 페이지 B가 사용
4. 기존 I/O 완료
5. Disk의 데이터가 Frame 10에 기록되어 페이지 B가 손상됨
```

이 문제를 막는 메커니즘이 **I/O Interlock**이다.
I/O가 진행되는 동안 관련 페이지를 **Page Locking 또는 Pinning** 상태로 두어 페이지 교체의 희생자로 선택하지 못하게 한다.

모든 페이지를 고정해서는 안 된다.
고정된 페이지가 많아질수록 운영체제가 교체할 수 있는 프레임이 줄어들고, 메모리 부족과 페이지 폴트가 심해질 수 있다.
필요한 페이지를 필요한 시간 동안만 고정하고 I/O가 끝나면 해제해야 한다.
